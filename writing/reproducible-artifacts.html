可复现研究 Artifact 的最小清单

可复现不是把代码压缩上传，而是为陌生的第三方设计一条从结论回到证据的路径。

“代码已经上传”经常被当作可复现的同义词。但站在复核者的角度，真正的问题是：我能否理解环境、找到入口、执行最短路径，并把得到的输出映射回论文或报告中的某个结论？

先定义复现目标

不同复现层级需要不同成本。把它们混在一起，会让轻量检查显得不充分，也让完整重训练显得遥不可及。可以先明确三层目标：

  1. 结构检查：配置、数据字段、脚本入口和输出映射是否完整。
  2. 证据复算：能否从发布的结构化结果重建表格、图和统计量。
  3. 端到端重现：在取得模型、数据和算力后，能否重新执行完整流程。

最小目录结构

目录名称应该向第一次打开仓库的人解释系统，而不是复刻作者机器上的历史。一个紧凑的起点可以是：

Artifact layout
artifact/
├── README.md              # 目标、入口与状态
├── REVIEWER_GUIDE.md      # 最短验证路径
├── MANIFEST.md            # 文件与论文结论映射
├── requirements.txt       # 轻量依赖
├── configs/               # 可审计配置
├── data/                  # 允许发布的样例或清理数据
├── results/               # 结构化聚合结果
├── scripts/               # 单一职责的命令行入口
├── src/                   # 可复用实现
└── tests/                 # smoke 与一致性检查

最重要的不是目录名字本身，而是每个文件都能回答“它支持哪一个检查”。

设计轻量验证路径

复核者不应在第一步就被要求下载数百 GB 模型或等待完整训练。Smoke test 可以优先验证那些不依赖 GPU 的结构性事实：

  • 编译或导入所有发布模块；
  • 从聚合 CSV 重新计算表格；
  • 用 toy input 检查命令行参数和数据流；
  • 确认配置引用的路径均为相对路径；
  • 扫描意外泄露的密钥、本地用户名与绝对路径。

一个好的 smoke test 应在普通 CPU 环境中完成，并清楚声明它验证了什么、没有验证什么。

写清边界，也写清安全

数据不能发布、模型受许可证限制或完整实验需要商业 API，都不应被埋在报错里。边界说明至少应覆盖：

  • 哪些资源来自外部，如何合法取得；
  • 哪些结果由发布数据直接支持；
  • 哪些模块是安全清理后的参考实现；
  • 哪些功能因滥用风险、隐私或双盲评审要求而排除。

诚实的范围声明不会削弱 Artifact；它让可验证的部分更可信。

发布前清单

  • 在一台干净机器或全新虚拟环境中执行 README；
  • 确认没有绝对路径、缓存依赖、私有数据和凭据；
  • 为每张关键表或图提供机器可读的源数据；
  • 固定随机种子，同时说明仍可能存在的非确定性；
  • 明确 license、第三方资源条款与研究状态；
  • 让未参与项目的人只按文档完成一次验证。

真正的目标不是让仓库显得复杂，而是让证据链变短。复杂训练可以昂贵，但理解一次实验为什么支持某个结论，不应该昂贵。
